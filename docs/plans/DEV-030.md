## 2. 正常会话区域收窄研究

### 当前源码

### 推荐目标

把正常会话入口合并到应用顶栏右侧，替换当前“受保护工作区”静态状态：

- 收起态：一个约36px高的状态按钮，显示状态点＋“会话正常”，可选短文本“MFA有效/待验证”；不再占据独立整行，也不推动业务页面下移。
- 展开态：锚定顶栏右侧的浮层，集中放置身份说明、重新核对、注销、按业务意图step-up和本地账号安全；浮层不改变页面布局。
- 路由切换、Escape、外部点击及操作完成后关闭；按钮使用`aria-expanded`/`aria-controls`，键盘焦点进入与返回明确。
- 小屏幕使用视口内宽度浮层；不把操作压成难点击图标。
- `checking/expired/changed/unavailable/logout-failed`等阻塞或异常状态仍使用独占gate，不能为了视觉收窄而让旧敏感页面继续显示。

这比继续压缩当前独立卡片更合适：状态归入全局导航语义，正常态零额外纵向空间；安全异常仍保持显著。

## 3. “可信登录与 MFA 设施未启用”原因

这不是CSS问题。当前本地账号模式只实现账号/密码登录与改密；`identity.Service.Available()`只在OIDC verifier存在时返回true。本地模式没有可签发`mfa_until`的第二因子，所以页面正确拒绝把密码登录伪装成近期MFA。结果是要求近期MFA的资料写入、授权管理和财务敏感操作不能在纯本地模式完成。

不能仅增加一个“已启用MFA”开关：客户端开关或数据库布尔值不能构成认证证明，会绕过现有安全边界。

## 4. 本地独立MFA方案

推荐首期采用**内置TOTP＋一次性恢复码**：验证、密钥保存和session签发全部由TeamLedger完成，不依赖OIDC、云KMS或网络MFA服务；用户只需任意标准离线Authenticator应用读取二维码。Authenticator应用是客户端，不是TeamLedger部署依赖。

设置画面放在顶栏会话浮层的“账号安全”中：

1. 用户以当前密码重新认证后开始登记；服务端生成CSPRNG secret和短时单次enrollment transaction。待确认secret与启用后的TOTP secret均使用keyd中独立identity MFA KEK做AEAD，AAD绑定org/account/factor/version；数据库只存密文、key ID/version和必要metadata。key不可用时fail closed，并把该domain纳入独立备份、恢复和轮换验证。
2. 页面显示`otpauth://`二维码及人工输入key；secret不写日志、URL history或localStorage，待确认transaction过期/取消/被替代即销毁且不可恢复。
3. “账号必须使用MFA”的政策状态与“当前存在有效因子”的状态分离。v13 migration把既有active本地账号置为`enrollment_required`；密码成功只能取得仅可访问账号安全登记端点的短时enrollment session，不能打开业务工作区、签发`mfa_until`或调用普通API。用户确认有效TOTP后，事务把factor generation切为active并撤销该账号其他session、旧`mfa_until`、旧恢复码及全部其他pending enrollment；旧因子不能并存。
4. 服务端生成一次展示的恢复码；只保存受keyd保护的MAC/digest，下载/复制后不能再次读取原文。恢复码不能直接登录、step-up或签发`mfa_until`；它只能与正确密码一起启动受限factor-recovery登记。消费、撤销当前/其他业务session和建立browser-bound recovery transaction在一个带idempotency receipt的事务完成；同一请求响应丢失可返回同一pending recovery，不会重复消费。并发消费只允许一个成功。
5. recovery transaction只能确认新的TOTP。新factor确认事务推进generation、作废旧TOTP和剩余恢复码、撤销其他pending transaction/session并生成新恢复码；确认前旧TOTP仍可由合法持有人登录，但所有开始recovery前签发的session及`mfa_until`已失效。重新生成恢复码则要求当前密码＋近期TOTP，只替换恢复码组并撤销其他session，不替换TOTP。
6. 后续普通登录要求密码＋TOTP；敏感step-up再次要求密码/TOTP并轮换session、CSRF及`mfa_until`，不自动重放业务操作。用户可在当前密码＋近期TOTP下主动替换TOTP；替换执行与recovery确认相同的generation/invalidation规则。
7. 遗失全部因子时只允许离线维护命令重置，避免普通管理员绕过MFA。离线重置保留`mfa_required`并切到`enrollment_required`，撤销全部session、旧因子/恢复码/pending transaction并记录独立审计；此后密码单独登录仍只能进入受限登记，取消或过期不能降级进入工作区。
8. 服务端限制尝试次数、时间漂移窗口和replay；同一time-step code不能重复用于登录或step-up。T5必须按操作验证初次登记、普通登录、step-up、主动替换、恢复码并发/幂等消费、恢复确认、恢复码重发和离线重置，对TOTP、剩余恢复码、当前/其他session、`mfa_until`及pending transaction逐项核对保留或撤销；覆盖响应丢失以及离线重置后密码单独登录不能进入工作区。

备选：WebAuthn/passkey抗钓鱼更强且不依赖外部服务，但需要HTTPS origin绑定、浏览器/设备凭据及恢复策略；同时交付TOTP＋WebAuthn会显著扩大迁移和恢复矩阵。应由用户明确选择。

## 5. Migration门禁

本地MFA需要新增账户因子、enrollment transaction、恢复码和TOTP replay状态，属于schema变化。依DEV-029：

- 不能修改v12 baseline；必须新建v13及SQLite/PostgreSQL前向migration。
- 实装前必须只读取得实际部署的应用commit、`schema_version`和checksum，登记source→v13 matrix。
- 必须先验证备份恢复，再验证带账户/会话/审计数据升级、中断/重启/重复执行、旧session撤销和新登录/step-up真实行为。

实际部署source尚未登记，因此本地MFA schema实装当前保持阻塞；会话顶栏收窄不改持久化，可独立推进。
