# PLAN · DEV-033 · 员工信息统一重构

- 日期：2026-10-16
- 状态：设计冻结，实装中
- 目标：按业务使用的中英文字段统一创建、批量上传、员工目录和员工详情；复用现有canonical profile/workforce/compensation事实，不建立第二套员工字段。
- 外部依赖：无。

## 1. 业务字段与唯一来源

| 业务显示 | canonical来源 | 录入/派生 |
| --- | --- | --- |
| 序号 / No. | 页面当前页行号 | 仅显示，不持久化 |
| 工号 / Staff Code | `employee_business_identifier(kind=staff_code)` | 必填；全集团唯一；允许换号和离职再入职复用既有人员工号的既定规则不变 |
| 姓名 / Staff Name | `profile.local_name` | 与英文姓名至少一个必填 |
| 姓名 / English Name | `profile.english_name` | 与本地姓名至少一个必填 |
| 地点 / Location | `employment_spell.location_code` | 必填；固定Shanghai/Wuxi/Tokyo |
| 所在公司 / Branch English | `employment_spell.legal_entity_id`→legal entity display name | 创建时选择法分公司 |
| 业务单元 / Business Group | Department在有效日的父链 | 只派生，不重复写入employee |
| 目前事业部 / Division | Department在有效日的父链 | 只派生，不重复写入employee |
| 目前部门 / Department | `job_assignment.department_id` | 创建时选择唯一Department |
| 学历 / Latest Education | 当前单一`education_record.level_code` | 必填；Master/Bachelor/Diploma |
| 雇佣起始日 / Date of Employment | employee lifecycle与初始employment的`valid_from` | 创建时同一入职日 |
| 职位 / Position | `job_assignment.position` | 必填职位title；继续按PII加密 |
| 职系 / Job Family | `job_assignment.job_family_id` | 必填；来自目录 |
| 职级 / Career Level | `job_assignment.career_level_id` | 必填；来自目录 |
| 直属主管 / HOD | administrative `reporting_line` | 可空；两者保持同一事实 |
| 调整前月基本工资 / Monthly base salary before | 查询日有效且已批准的`monthly_base_salary` | **不复制到人员主数据**；只在具有独立财务授权/MFA的调薪或个人薪酬画面读取 |

薪资隔离是安全边界，不是遗漏：组织/PII权限不能借员工目录获得金融正文。后续调薪重构直接读取现有批准薪资事实并显示历史。

## 2. 单人创建

扩展既有OP-ORG-05可选请求字段，不新增表：

- `employment:{legal_entity_id,location_code}`
- `education:{level}`
- `job_assignment:{department_id,job_family_id,career_level_id,position:{title}}`

TeamLedger页面切换为完整创建，以上三组与Staff Code、姓名、入职日均必填，HOD及退职日可空。服务将profile、employee lifecycle、identifier、employment(kind=`hire`)、education、job assignment及可选administrative reporting组装为既有workforce items，在同一个OP-ORG-05事务、receipt及audit中提交；任一目录、唯一性、授权、关系或revision失败整笔回滚。既有API调用若不提供新增组仍保持合法，内部批量上传在本task完成后全部切换到完整组。

Business Group和Division不接受自由输入；UI从固定`Business Group → Division → Department`有效父链展示并提交Department ID，避免四份组织字段漂移。
创建表单的目录选项以入职日为有效日读取；入职日变化会清除旧选择并重新读取，不拿顶部查看日期替代事实生效日。服务端事务继续按每个workforce item的`valid_from`重验目录有效期与Department父链，preview或客户端解析结果不是授权/一致性依据。

## 3. 批量模板与预览

`Employees`唯一工作表改为用户可识别的双语表头：

1. `工号 Staff Code`
2. `姓名 Staff Name`
3. `姓名 English Name`
4. `地点 Location`
5. `所在公司 Branch Code`
6. `业务单元 Business Group Code`
7. `目前事业部 Division Code`
8. `目前部门 Department Code`
9. `学历 Latest Education`
10. `雇佣起始日 Date of Employment`
11. `职位 Position`
12. `职系 Job Family Code`
13. `职级 Career Level Code`
14. `直属主管 HOD Staff Code`
15. `退职日 Departure Date`
16. `业务邮箱 Work Email`
17. `业务电话 Work Phone`
18. `资料摘要 Profile Summary`

Branch/BG/Division/Department/Job Family/Career Level使用稳定code；preview按**每行Date of Employment**解析到唯一有效ID并验证该日的Department父链与工作簿填写的BG/Division一致，返回解析使用的catalog revision。错误code、该入职日无效/过期目录、层级不一致或重复Staff Code均逐行报错且不创建。确认创建时服务端仍在同一OP-ORG-05事务按各初始事实`valid_from`重新核对目录和层级，不能信任preview；并发变化返回冲突后必须重新预览。最多100人、XLSX安全边界、逐行幂等、主管末段一次原子写入及结果不确定恢复沿用DEV-032。创建body增加解析后的employment/education/job assignment，仍不接受薪资列。

## 4. 员工目录与详情

- 员工目录按业务列展示：No.、Staff Code、中英文姓名、Location、Branch、Business Group、Division、Department、Latest Education、Date of Employment、Position、Job Family、Career Level、HOD；保持既有服务端cursor分页。
- 宽表放在有边界的横向滚动容器；移动端不造成页面级横向溢出。
- 员工详情使用相同字段顺序和双语title，不显示内部UUID作为主视觉；数据状态/revision收进折叠区。
- 法分公司、组织单元、Job Family、Career Level和HOD尽量显示当前获准label/name＋code；无PII正文权限时维持既有metadata降级，不扩大授权。
- 查询日继续使用顶部全局查看日期；目录和详情均按同一有效日投影。

## 5. Migration与兼容

本task不新增schema，因此不增加migration。既有环境中历史员工可能缺employment/education/job assignment；目录/详情明确显示“未维护”，不伪造默认值。新建人员和新版模板要求完整字段，逐步通过既有OP-ORG-10维护旧记录；不做隐式merge。

## 6. 验收

1. 单人创建一次请求原子得到完整员工主数据；任一目录/Staff Code/HOD失败零残留。
2. 批量模板为18个双语表头；preview解析并展示全部输入及派生层级；创建后详情回读一致。
3. 目录默认/筛选/前后分页不变，宽表完整显示业务字段。
4. 详情不再以法分公司/Department/Job Family/Career Level UUID作为主要内容。
5. 人员API、目录、详情和模板不释放薪资；调薪页面独立授权读取。
6. SQLite真实API、共享PostgreSQL contract、Go全包编译、Web全量测试、production build及真实浏览器桌面/390px smoke通过；无PostgreSQL DSN时明确记录未实测。
