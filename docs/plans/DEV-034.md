# PLAN · DEV-034 · 调薪批次业务化重构

- 日期：2026-10-16
- 状态：已完成
- 目标：把现有技术型调薪批次页重构为可直接使用的Normal/Special批量录入工作台；按Staff Code解析员工资料，先服务端预览并显式确认，再原子写入保留历史的薪资事实。
- 外部依赖：无。SQLite/PostgreSQL、Vue及同部署本地keyd内独立完成。

## 1. 现状问题与保留能力

现有实现已有`N/S-{year}-{sequence}`业务编号、Normal/Special规则、Salary Range、XLSX隔离candidate、冻结manifest、整批原子激活和已激活批次correction，但页面仍要求法分公司/员工UUID及XLSX，缺少业务批次名、预算、Staff Code逐行录入、员工资料回填和调整前工资不一致确认；不一致目前直接`409`，无法完成用户要求的保留历史纠正。

本task保留以下安全边界：批次不是逐员工HTTP循环；最多500名唯一员工；Money为CNY/JPY、scale 0非负整数；增加额不允许负数；无FX；最终激活仍为一个数据库事务；任一员工、授权、组织、Salary Range、薪资basis或密钥依赖失败均整批零生效；financial/PII正文不进URL、日志或浏览器持久存储。

## 2. 批次表头

创建批次时录入：

| 字段 | 规则 |
| --- | --- |
| 批次名 | 必填，1..200 UTF-8 bytes；与服务器不可编辑业务编号分开 |
| 年度/类型 | `cycle_year`及`normal/special`；每年批次数量不限 |
| 法分公司 | 从有效legal entity目录选择，不再手填UUID |
| 默认生效日 | Normal/Special均必填完整日期；Special逐行可指定月份，空值继承默认生效日所在月 |
| Special理由 | Special批次必填受控`reason_code`＋自由文本；逐行空值继承批次值，逐行同时填写时覆盖两者 |
| 整体预算 | 必填currency（CNY/JPY）＋scale-0非负整数；**仅参考，不阻止超预算**，保持既定“暂不设置预算约束/审批”决策 |

预算只与同币种increase合计比较；其他币种单独列出且明确“无FX、不可合并”。批次名、理由和预算属于financial正文，以新版本envelope payload保存；批次metadata表只保留编号、类型、实体、日期、状态、revision及payload引用。

## 3. 逐行录入与员工回填

- 新建/打开空草稿默认显示3个空行；可追加至500行、可删除，提交预览时全空行忽略，半填行逐项报错。
- 用户只输入Staff Code；服务端按集团唯一、指定生效日有效的staff identifier解析唯一employee，客户端不得指定或覆盖Employee ID。
- Staff Code失焦后，页面以`organization_management`目录查询回填Staff Code、中英文姓名、Location、Branch、Business Group、Division、Department、Position、Job Family、Career Level，再以个人薪资读取显示当前月基本工资；这些请求只作操作辅助，不形成批次basis。
- 最终preview在financial授权边界按Staff Code重新解析employee、identifier/任职/Salary Range/current term并冻结revision；姓名/职位正文另过当前PII读取闸门，无PII权时不得通过财务权限扩大可见范围。
- Normal逐行字段：绩效等级（手工必填）、平均调薪幅度和部门建议幅度（仅参考）、调整前工资、增加额、调整后工资；生效日默认批次日期并可逐行覆盖。
- Special逐行字段：生效月份、调整前工资、增加额、调整后工资、受控理由、自由文本；月份/理由空值继承批次默认。显示该员工当年度及上一年度Normal＋Special已生效次数。
- 调整后工资必须精确等于调整前工资＋增加额；全部金额为规范整数字符串，客户端只辅助计算，服务端为唯一判定。
- 原XLSX能力保留并改为相同Staff Code输入契约；手工行与XLSX均进入同一个服务端candidate/preview路径，避免两套校验。

## 4. 预览、警告与确认

新增JSON手工candidate入口并复用OP-COMP-08的24小时隔离candidate。服务端规范化空值、解析employee/组织/Salary Range/current terms，返回：

- 逐人业务资料和规范金额；
- Normal/Special专属字段及年度次数；
- CNY/JPY增加额合计、预算同币种差额和其他币种不可比提示；
- 行级错误；
- `SALARY_BEFORE_MISMATCH`警告：录入调整前工资、系统权威工资及有效日期；
- 冻结的identifier/employment/assignment/range/current term identity与revision。

预览不改草稿和薪资。无错误且无警告可直接确认应用；存在工资不一致时，确认画面必须逐行明确勾选“先纠正系统当前工资，再调薪”。应用请求绑定candidate ID、batch revision及被确认员工集合；漏确认、额外确认、过期candidate、并发revision变化均拒绝。应用后生成新draft revision与manifest；激活前仍需第二次整批确认，页面切换/上传/预览/保存均不自动生效。

## 5. 调整前工资不一致的历史处理

不覆盖term、不patch原event。对已明确确认且满足自动纠正条件的行，最终激活事务依次：

1. 锁定全部员工、批次service subject及Salary Range；重验当前授权、candidate冻结basis和manifest。
2. 当前权威term必须仍是预览时的同一term/revision，且currency、scale、month/monthly/gross口径相同；不存在当前工资、币种/口径不同、同日已有薪资事件或存在未来排程时不猜测，整批返回冲突并要求先走独立薪资纠错。
3. 追加`correction_replacement`，以原事件日期把当前term金额纠正为录入的`salary_before`；原event/term保留，纠正事件链接到本批次但不计入调薪次数。
4. 再以批次/行生效日追加Normal/Special adjustment，从纠正后的term到`salary_after`；正增加计入调薪次数，零增加只保留已确认的纠正结果。
5. correction、adjustment、schedule、batch event、activation、receipt和audit/outbox在同一事务提交；任一步失败全部回滚。

未发生不一致的行继续要求录入`salary_before`精确匹配当前term。激活前出现任何basis漂移进入`activation_conflict`，不得用旧确认自动覆盖。

## 6. Migration与既有环境

从已部署v12做前向v13 migration，禁止要求清库：

- migration引擎接受并严格校验v12 source checksum/结构后，在一个事务升级v13；空库仍顺序安装至v13。
- 新增不可变、可rewrap的批次header financial payload及其owner/maintenance/no-delete/update guard；批次表增加header payload引用。
- batch line/import v1 envelope以向后兼容方式追加预览警告、纠正确认和冻结current-term字段；v12既有payload缺少新字段时按零值读取，不改旧密文。
- v12既有批次保留空header引用；读取时生成只读迁移视图：显示名取business code、预算标记`legacy_unspecified`、Special保持原逐行日期/理由。新建v13批次写加密header并执行新必填规则。SQL migration不依赖运行中的keyd，也不伪造预算。
- SQLite与PostgreSQL migration均永久测试：v12实际样本升级后员工、批次、密文、event、receipt和audit数量/关键值不变；错误checksum/中断原子回滚。
- 新payload加入financial key inventory、rewrap、backup/restore及schema reference校验，不能形成密钥维护盲区。

## 7. 页面结构

`P-COMP-01 /orgs/:org_id/compensation-adjustments`拆为三个视觉层级：

1. **批次列表与创建**：业务名、编号、类型、实体、默认日期、预算、状态、逐人数量；目录选择，不展示UUID主视觉。
2. **批次录入工作台**：固定批次摘要；默认3行可增删的横向业务表；Staff Code解析状态、员工资料、金额与类型专属列；XLSX作为次要入口。
3. **预览确认**：错误、工资不一致警告、预算/币种摘要、逐人确认；应用草稿后显示冻结摘要，再显式整批生效。

Salary Range维护移入独立折叠区，避免抢占主要工作流。已激活批次更正移除原始JSON textarea，至少保持为受控表格；若本task无法安全覆盖全部历史纠错成员编辑，则只读展示既有更正入口并保留API，不向普通用户暴露JSON。

页面复用全局设计token、语义表格、键盘焦点、ARIA状态及局部横向滚动；桌面与390px不产生页面级横向溢出。敏感candidate、工资和员工详情只在当前页面内存，离页/session失效清空并取消请求。

## 8. API与状态机

- OP-COMP-06：列表/详情返回获准解密后的header及line preview字段。
- OP-COMP-07：创建新header，服务器分配稳定业务编号并密封financial payload。
- OP-COMP-08：XLSX或JSON手工行建立同构preview candidate；Staff Code解析接口使用同一OP/授权且只读不落业务事实。
- OP-COMP-09：以candidate＋不一致确认集合replace-all草稿；不再信任客户端Employee ID/basis。
- OP-COMP-10：显式submit/retry及已激活纠错；激活内可执行已确认的前置salary correction。
- OP-COMP-11：Salary Range不变。

状态保持`draft → activated`，依赖不可用为`activation_blocked`，basis漂移为`activation_conflict`；两者都不得有部分薪资事实。业务编号、已激活批次、原event/term不可修改或删除。

## 9. 验收

1. 创建Normal/Special批次可保存业务名、法分公司、默认生效日、Special默认理由和参考预算；编号仍由服务器唯一分配。
2. 草稿默认3空行；输入Staff Code后回填员工和当前工资；增删、多行、空行忽略、重复员工及500行边界正确。
3. Normal与Special字段/default/手工覆盖、非负整数、次数提示、混币及参考预算摘要正确；不进行FX或预算阻断。
4. 手工及XLSX经过同一服务端preview；任何错误不应用，工资不一致必须逐行确认。
5. 不一致确认后，单事务先追加历史纠正再追加adjustment；原event/term仍可查询，未确认或basis漂移零生效。
6. v12 SQLite/PostgreSQL样本原地升级v13且数据保持；fresh install、key inventory/rewrap/backup schema检查通过。
7. 定向双后端API、Go全包编译/测试、Web全量测试/build，以及真实Chromium桌面/390px创建→3行录入→预览→确认smoke通过；无PostgreSQL DSN时明确记录未实测。
8. FUNCTIONAL_SPEC、TECHNICAL_SPEC及Mermaid财务数据流同步，不再描述“无budget字段”或仅XLSX技术页面。
