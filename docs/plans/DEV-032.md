# PLAN · DEV-032 · 人员资料批量上传与模板

- 日期：2026-10-16
- 状态：设计冻结，实装中
- 目标：在“人员资料”创建页提供可下载的`.xlsx`模板、上传前校验与预览、明确确认后的批量创建，以及不掩盖部分成功的逐行结果。
- 外部依赖：无；模板生成、工作簿解析和创建均由TeamLedger本体完成。

## 1. 范围与字段

批量入口与单人创建使用同一业务边界，不借批量入口维护任职、部门、学历或薪资。模板第一张工作表固定为`Employees`，第一行为以下稳定字段：

| 列 | 必填 | 规则 |
| --- | --- | --- |
| `staff_code` | 是 | 全集团唯一；规范化后1..64字节；文件内重复直接阻止创建 |
| `local_name` | 条件必填 | 与`english_name`至少填写一个 |
| `english_name` | 条件必填 | 与`local_name`至少填写一个 |
| `email` | 否 | 业务邮箱；沿用单人创建profile校验 |
| `phone` | 否 | 业务电话；沿用单人创建profile校验 |
| `profile_summary` | 否 | 资料摘要；沿用单人创建profile校验 |
| `manager_staff_code` | 否 | 直属主管/HOD的Staff Code；可引用当前系统员工或同一工作簿员工 |
| `hire_date` | 是 | `YYYY-MM-DD`文本，映射`lifecycle.valid_from` |
| `departure_date` | 否 | `YYYY-MM-DD`文本且晚于入职日，映射`lifecycle.valid_to` |

模板只提供表头和说明，不放会被误导入的示例人员。模板下载需要当前组织管理写权限；响应`no-store`且不含租户数据。

## 2. 安全解析与预览

1. 接受标准`.xlsx` MIME，原始压缩体不超过5 MiB、展开不超过20 MiB、ZIP entry不超过1,000、有效人员不超过100。
2. 复用有界XLSX包/XML解析器；拒绝公式、cached formula、numeric/date serial、未知cell type、重复/缺失表头、额外非空列和损坏包。XML硬性拒绝DTD、实体声明、XInclude及任何外部关系解引用；解析器不发起文件或网络访问。所有输入字段必须是文本；日期不从Excel locale或时区推断。
3. `POST /api/v1/orgs/:org_id/employees/import-preview`只返回规范行与有限安全错误，不创建employee、不保存原工作簿、不写数据库。PII不会进入URL、日志或审计正文。
4. UI选择文件后必须先“校验并预览”；文件变化立即清除旧预览。没有有效预览不能创建。
5. 预览展示行号、Staff Code、姓名、主管Staff Code、入职/退职日及错误；敏感联系方式不在整表重复展示。

## 3. 明确确认与创建语义

不新增schema或服务端candidate，因此既有v12环境不需要migration。浏览器只在当前页面内保存规范预览、每行幂等键和执行状态；刷新、崩溃或离开页面后不能自动恢复，UI不得承诺跨页面恢复。

确认后按以下步骤执行：

1. 在任何创建前重新核对同一subject/org/session，确认org级`organization.read/write`与`pii.read/write`，并固定当前catalog/graph revision。包含主管关系时必须先完成全部主管解析和下述环检查；无权读取/维护任一主管的文件禁止开始，不以先创建无主管人员降级。
2. 解析所有`manager_staff_code`：先匹配同一工作簿的唯一`staff_code`，其余以当前业务日的在职员工目录精确匹配。不存在、不可读、退职或歧义的主管使对应行失败；不得猜测。同批自引用和闭环在创建前拒绝。既有图不可能预先引用尚未创建的新员工；最终OP-ORG-10仍执行服务端完整环及并发校验。
3. 对每行使用稳定、随机、仅内存保存的幂等键调用既有OP-ORG-05。创建profile、lifecycle和Staff Code仍是单行原子事务；此阶段不写主管关系，避免每行推进graph/auth epoch。每次成功都消费回执中的实际`workforce_revision`，不得假定固定版本。
4. 所有可创建行处理完成后，只把“员工与主管两端ID均已确认”的关系纳入最终命令：同批主管创建失败或结果不确定时，其下属标记“已创建，主管待维护”，不得把并发占用相同Staff Code的既有员工自动认作主管；其他独立且两端已确认的关系仍可继续。若graph revision未被外部并发推进，以一次OP-ORG-10写入这些administrative reporting关系；请求冻结实际employee revisions、catalog/graph revision、完整body及独立稳定幂等键，最多100项且只推进一次graph/auth epoch。结果不确定时只在重新核对同一subject/org后重放原key＋原body，不构造新命令；没有可确认关系时不发送空命令。
5. 批量操作不是整批数据库事务：Staff Code并发冲突或单行资料错误只失败该行。主管关系批次若因最终并发检查失败，人员仍保留且结果标记“已创建，主管待维护”；绝不把部分成功显示为整批失败。
6. 页面固定展示`已创建 / 已创建但主管待维护 / 失败 / 结果不确定 / 未处理`逐行结果和汇总。当前页面内的结果不确定命令保留原key和body，只允许“确认原提交”。刷新/崩溃后无法证明未知命令归属：重新上传发生Staff Code冲突时不得自动认领既有员工，须到员工目录按Staff Code人工核对并手工维护主管。
7. 每次批量最多100人。执行期间禁止切换文件或重复启动；离开页面前提示尚有未完成/不确定命令。

## 4. API

| 操作 | 方法与路径 | 权限 | 结果 |
| --- | --- | --- | --- |
| 下载模板 | `GET /api/v1/orgs/:org_id/employees/import-template` | OP-ORG-05同等org级`organization.write`＋`pii.write` | XLSX attachment；无租户数据 |
| 校验预览 | `POST /api/v1/orgs/:org_id/employees/import-preview` | 同上，且CSRF/same-origin | `{rows, errors, row_count}`；零持久化 |
| 执行创建 | 复用`POST /api/v1/orgs/:org_id/employees`及最终`POST /workforce-changes` | 既有OP-ORG-05/10 | 既有receipt、audit与权限模型 |

preview不是mutation，不使用Idempotency-Key；但因为HTTP POST上传敏感正文，仍要求CSRF和same-origin。结构/容量错误返回422；业务行错误以200预览响应返回并禁止创建。

## 6. 非目标

- 不导入组织任职、Branch、Location、Business Group、Division、Department、学历、Job Family、Career Level或薪资；这些继续由组织/薪资模块维护。
- 不保存原始XLSX，不建立长期import candidate，不新增数据库表。
- 不自动覆盖既有员工，不把重复Staff Code解释为更新。
- 不执行公式，不自动转换Excel日期或locale格式。
