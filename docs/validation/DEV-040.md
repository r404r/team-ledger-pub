# DEV-040 验证摘要 · 明确授权管理可用性

- 日期：2026-10-16
- 结论：授权API原本已实现；故障是Web未接受v15新增的合法bootstrap安全grant和`identity.manage` authority。前端契约已与服务端收敛，无migration或数据修复要求。

## 1. 失败复现

新增真实页面级回归，向P-SEC-01提供bootstrap管理员响应：

- session具有`access_grant.manage`和近期MFA；
- authority包含`identity.manage / audit / security_administration / org`；
- grant列表包含`access_grant.manage`和`identity.manage`。

修复前页面稳定进入通用“服务或网络不可用”alert，授权列表不存在。根因是`grantPairs.ts`旧allowlist拒绝上述两项，不是GET/POST `/api/v1/access-grants`未实现。

## 2. 自动验证

| 命令 | 结果 |
| --- | --- |
| `cd web && bun run test -- GrantPage.test.ts` | 83/83通过；覆盖bootstrap安全grant读取、identity authority预览及既有授权竞态/拒绝路径 |
| `cd web && bun run test` | 12 files、285/285通过 |
| `cd web && bun run build` | `vue-tsc --noEmit`及Vite production build通过；104 modules transformed |

回归明确区分：`identity.manage`是当前bootstrap authority可签发能力；`access_grant.manage`是可读取/筛选但不能由普通授权命令签发的固定管理事实。

## 3. 真实浏览器

以production Vite产物和完整v15 bootstrap形状运行真实Chromium（1440×1000）：

1. 打开`/security/grants`，无“服务或网络不可用”alert。
2. “当前批准的委派范围”显示`audit.read`、`identity.manage`两项bootstrap authority。
3. 授权列表显示7项bootstrap grant，包括`access_grant.manage / audit`和`identity.manage / audit`。
4. category筛选包含`audit`，purpose包含`security_administration`，capability包含`access_grant.manage`和`identity.manage`。
5. 点击“新建授权”，选择bootstrap identity authority，填写非自身主体和批准期限，页面成功进入`identity.manage / audit / security_administration`确认预览；预览前未发送命令。

## 4. 保持的安全边界

- Web未知安全tuple仍拒绝整个DTO，不用宽松字符串绕过。
- `access_grant.manage`没有加入普通可签发能力；服务端既有禁止保持。
- 管理工作台只消费后端实时返回的authority交集，不推导或创建业务authority。
- 401/403/404、MFA失效、authority变化、auth epoch冲突及不确定提交继续清空或要求显式重试。
