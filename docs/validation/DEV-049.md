## 门禁瓶颈与修复

首次全量验证未通过，其失败已定位并处理：

- 原测试PostgreSQL的默认锁容量在并发迁移时出现`out of shared memory`。最终采用独立TLS测试实例，`max_locks_per_transaction=1024`、`max_connections=200`；产品配置及既有部署数据未改。
- 标准race首次执行遇到SQLite API启动15秒观察超时、identity维护命令超时和大型package默认10分钟时限。未修改的`3e88c61`也复现同一启动失败。CPU采样显示新增SQLite提交回归约79秒，其中约49秒用于重复迁移构造，主要成本来自真实SQLite解释器的race/指针检查。
- 仅缓存按版本由内嵌冻结migration成功生成的SQLite参考定义；每次校验仍读取目标库实际catalog、ledger和foreign key状态。测试fixture复用真实迁移产生的空schema字节，复制后执行真实校验及独立业务/安全seed；真实升级测试保留。
- API启动smoke编译并运行实际程序，继续验证受保护TLS key、keyd及双数据库行为；service/API业务并发路径由完整race套件验证。
- `go test -race ./cmd/api ./internal/store -run 'TestAPIStartupRequiresProtectedTLSAndLocalKeyd|TestRuntimeSchemaDriftFailsStartupWithoutRepairingFacts' -count=1`通过。既有schema drift测试覆盖首次成功校验后修改schema仍拒绝、重开也拒绝且不修复，证明缓存没有复用目标库的检查结论。
- 最终全仓race另暴露既有OIDC并发回调偶发失败。SQLite身份事务在读mode后取writer存在WAL快照升级窗口，现先取得mode写锁，再按mode→org→subject顺序授权。原有8路回调测试增加共同开始barrier并保持恰好一个会话的断言；`go test -race ./internal/identity -run '^TestOIDCStateBrowserPKCEExpiryOnceAndConcurrentCallbacks$' -count=3`双库连续通过。
- 复现并修正既有调薪preview测试把当前业务日写死为`2026-10-16`的问题：改用注入测试时钟`f.Now`，业务实现未改。
