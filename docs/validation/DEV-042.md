# DEV-042 · 人员XLSX逐格错误诊断验证

- 日期：2026-10-16
- 结论：已修复使用最新模板、经Excel保存后整份文件只显示通用解析错误的问题；解析与页面现在给出安全的工作表、单元格、固定错误原因和request ID。

## 根因

Excel可把用户输入保存为显式OOXML类型，例如数字/日期单元格的`t="n"`或`t="d"`。旧解析器只把省略`t`的数字识别为“非文本”，却把显式类型当作未知工作簿结构并终止；API随后把具体原因收敛为`INVALID_INPUT`，页面再统一显示“工作簿无法安全解析”，因此无法定位。

## 修复后的契约

1. `t=n|d|b|e`是可解析但非文本的单元格，进入preview的逐格`text_required`错误；不会执行、转换或猜测Excel日期序号。
2. 公式、损坏结构、外部关系、宏、错误表头等仍拒绝整份工作簿。422响应在既有`code/request_id/reason`之外增加`workbook_error`：固定`code`及可选安全`sheet/cell`。
3. 页面把逐行和结构错误显示为`Employees!J2`一类位置，并给出中文处理方法；结构错误同时显示request ID。
4. API日志写`PERSONNEL_IMPORT_REJECTED request_id=... sheet=... cell=... code=...`。不记录单元格内容、公式、relationship target、压缩包内部路径或人员PII。
5. 未认证、无权限、上传过大、目录冲突和服务不可用分别显示对应错误，不再全部伪装为模板解析失败。

## 验证证据

- `go test ./internal/xlsx ./internal/organization -run 'Test(ReadFirstSheet|ParsePersonnelWorkbook)' -count=1`：通过；覆盖显式`t="n"`、公式`Employees!B1`安全诊断及人员行`Employees!J5`文本错误。
- 使用真实TLS PostgreSQL 17和SQLite执行人员模板/preview API定向回归：通过；错误表头返回422、`Employees!A1/header_mismatch`及合法request ID。
- `bun run test -- PersonnelImportPanel.test.ts`：4项通过；覆盖422结构错误和200逐行错误的sheet/cell呈现。
- `bun run build`：production TypeScript检查和Vite构建通过。
- production Vite产物经真实Chromium选择XLSX并触发preview：页面实际显示`Employees!J2：不允许公式；请将该单元格转换为纯文本（请求 ID：…）`，文件仍保留并可重新校验。
